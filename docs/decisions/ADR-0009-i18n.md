# ADR-0009 · Internationalization with a typed in-house catalog

- **Status:** accepted
- **Date:** 2026-09-21
- **Deciders:** Raúl López

## Context

The UI has been English-only since OG-014, with strings hardcoded in the
components. M20 makes the language a choice (English and Spanish first). We
need a mechanism that:

- keeps the keys and their parameters checked at compile time, so a typo or a
  missing translation fails `typecheck` instead of showing a raw key;
- does not re-render or look up a message per graph/log row: the log can render
  thousands of rows and the graph runs on animation frames;
- fits `AGENTS.md` rule 5 (no new dependency without justification), for two
  locales and a few hundred strings;
- leaves the English rendering unchanged.

Rust also produces user-facing text (operation labels, error messages). Git's
own output is never translated.

## Decision

Internationalize on the frontend with a **small in-house, typed message
catalog** and no new runtime dependency. A `Messages` type defines every key;
`en` and `es` are objects of that type, so a missing or extra key is a type
error. A `useI18n()` hook exposes `t(key, params?)` from the active locale,
held in a store and persisted with the existing settings mechanism. Dates and
numbers use the built-in `Intl` API.

User-facing strings coming from Rust are **not** translated as text: the
frontend maps a `GitError` (or another typed result) to a catalog message by
its `kind`, so the backend stays language-neutral.

## Alternatives considered

- **`i18next` + `react-i18next`** — mature and featureful, but two runtime
  dependencies, a plugin/loader model and async resource resolution for what
  are two static catalogs; overkill for this size and contrary to rule 5.
- **`react-intl` (FormatJS)** — ICU message syntax and CLDR plural rules, very
  heavy for two locales; its value shows with many languages and professional
  translation tooling, which we do not have.
- **Build-time extraction/compiler (e.g. `i18n-ally`, `gettext`)** — adds
  tooling and a build step without solving anything the typed catalog does not.
- **Translate the Rust strings at the source** — a translated backend would
  leak the UI language into the core and duplicate the catalog; discarded.

## Consequences

- Adding a locale is one catalog file plus one member of the locale union; a
  missing key fails `typecheck`.
- No ICU: plurals and interpolation use a tiny helper (`{name}` substitution
  and a `.one`/`.other` shape where needed). If a future locale needs real
  plural rules or gender, revisit and possibly supersede this ADR.
- The dependency list and the bundle stay unchanged.
- Components stop containing literal UI text; tests keep asserting the English
  rendering, and new tests cover the Spanish one.
- Rust must expose enough structure to render messages (error `kind` and
  fields) instead of a pre-formatted localized string; today's typed errors
  already do this.
